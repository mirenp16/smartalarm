## Automated evidence

`python3 scripts/test.py 3` compiles release and test builds for `fr265s` and
executes 30 native tests per run. The final series passed all 90 test executions
on SDK 9.2.0. Both builds completed without
compiler warnings and `git diff --check` passed. Logs are generated in
`bin/validation/tests-1.log` through `tests-3.log`.
The suite uses synthetic sensor inputs through production ingestion methods;
it does not duplicate the algorithm in Python. Detector setup and simulated
clock helpers are excluded from release builds by the `testSupport` annotation.
The test build replaces only clock/offset reads; calendar and alarm decisions
run through the production scheduler and store.

The runner checks the complete success footer and expected test count because
the installed SDK's `monkeydo` can return exit code 1 even when every test passes.
A missing footer, test failure, timeout, or incomplete run fails validation.
The runner retries startup connection failures because macOS can return from
launching the simulator before its listener is ready. It never retries a failing test.

## Limits and device checks

No review or simulator suite can establish that software has no bugs. These
tests do not validate physical sensor accuracy, overnight battery consumption,
sound/vibration on the watch, or every UI transition.

Midnight windows and offset transitions now have dedicated tests. Calendar keys
encode local dates/times; deadlines are recalculated using the watch's current
offset. One-time records store their offset to preserve the intended local time.
An upgraded legacy one-time alarm has no original offset to recover, so its
first migration assumes the current offset; verify saved times after upgrading.

The app does not forecast offset changes or recover arbitrary manual clock
resets. Forward-jump recovery requires active evaluations no more than two
minutes apart and lasts 15 minutes. Only one alarm rings at a time; another
alarm can expire while the first is sounding. Eight completed occurrences per
alarm are retained, covering ordinary repeated-hour and adjacent-date changes,
not arbitrary travel far backward in calendar time. No future-transition GPS
lookup or extra location permission is used. See the README for user-facing policy.

On the watch, verify a short alarm while walking before its window; then verify
an alarm with no early-wake evidence reaches its deadline, snooze works, the
passcode dismisses it, and an unfinished Active Alarm exit prompt is interrupted
by a due alarm. Finally test overnight with the usual settings and note the
heart-rate status, target/window, actual firing time, and any app interruption.
Keep a native Garmin backup alarm during that validation.
