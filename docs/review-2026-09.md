| Output | Contents |
|---|---|

The runner rejects incomplete results and changes to validation inputs during a
run. It uses a binary hash in the simulator executable's filename to avoid
reusing an older loaded suite. It retries connection failures, not failed tests.
Success requires the complete passing footer and expected test count because
this SDK's simulator launcher can return exit code 1 even when tests pass.

## What the tests cover

Tests call the production scheduler, store, and detector with synthetic sensor
inputs and a controlled clock. Test helpers are excluded from release builds.

| Area | Coverage |
|---|---|
| Wake detection | Already-awake input, walking and its expiry, missing/stale HR, warm-up, buffer bounds, peak/decline, and long gaps |
| Deadlines | Every 15-second evaluation across all four windows with no HR; initial ring at the target and duplicate suppression |
| Reported morning | Baseline input from 4:15, elevated HR from 4:36, and a 5:15 ring for a 6:00 alarm |
| Rearming | Dismiss at 5:38; reopen at 5:38, 5:59, or 5:59:59; wait for 6:00 despite awake evidence; reopening at 6:00 leaves it completed |
| Recovery | Saved rearming and one-time snooze across reload; stale/invalid ringing; preservation of pending ringing and snooze |
| Calendar | Midnight windows, snooze counts across midnight, offset changes, skipped/repeated hours, and legacy state migration |
| Scheduling and settings | All 127 nonempty repeat masks across seven day offsets, overdue backups, earliest eligible target, 20-alarm capacity, deletion, edits, passcodes, and picker bounds |

The reported real-world 5:38 firing cannot be attributed to one cause without
watch logs. The synthetic morning test verifies a defined input sequence; it
does not prove what the watch measured that night.

## Rearming policy

Reopening Active Alarm Mode before an enabled repeating alarm's completed target
rearms that occurrence for its set time. It preserves completion history for
other dates and skips early-wake scoring for the rearmed occurrence. The new
state survives reload and clears when that occurrence rings.

Reopening at or after the target leaves it completed. Current ringing and snooze
recovery take precedence, and disabled alarms remain disabled. Fresh alarms and
later repeats retain normal early-wake behavior. Once alarms turn OFF when they
ring and must be explicitly enabled and saved to schedule them again.

## Limits and watch checks

The app runs in the foreground. Tests do not establish sleep-stage accuracy,
physical sensor behavior, overnight battery consumption, sound/vibration, or
correct behavior for every UI transition.

Calendar calculations use the current local offset, not future transition rules.
Forward-jump recovery requires active checks no more than two minutes apart and
lasts 15 minutes. Only one alarm rings at a time; another can expire while it is
sounding. The store retains eight completed occurrences per alarm, so it does
not provide unlimited duplicate protection after travel far backward in time.
An upgraded legacy Once alarm has no original offset to recover; migration
assumes the current offset, so verify saved times after upgrading.

On your Forerunner 265S, check:

1. An early wake while walking inside the window, and a deadline ring without
   early-wake evidence.
2. Snooze, passcode dismissal, and a due alarm interrupting an unfinished exit
   code prompt.
3. Reopening during a short snooze to confirm recovery.
4. Dismissing early, then reopening one minute before the target: it should wait
   for the target. Reopening at the target should leave that occurrence completed.
5. An overnight run with your usual settings. Note the HR status, window/target,
   actual ring time, and any app interruption. Keep a native Garmin backup alarm
   during validation.
