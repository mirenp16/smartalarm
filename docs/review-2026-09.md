## Additional deadline-focused review

The subsequent three passes revisited the maintained-file inventory above:

1. Read and trace behavior, including the scheduler's unconditional deadline
   branch, sensor fallbacks, editor saves, and view transitions.
2. Check boundary and interaction cases. A new native regression reproduced
   rearming an 11:55 pm repeating alarm at 12:02 am incorrectly firing yesterday's
   occurrence. Rearming now suppresses that past occurrence while an unchanged
   alarm retains its grace period. Next Alarm also now compares a pending snooze
   with the next regular target, matching the countdown when a backup is earlier.
3. Verify callers, framework callbacks, resources, configuration, tests, and
   documentation against the changes. All six PNGs have valid chunk checksums
   and declared references; no maintained file is unused. Removed seven unused
   imports and ignored compiler-generated `mir/` and `internal-mir/` folders.

The added deadline test advances through every 15-second evaluation for each
supported window with missing HR throughout: no early ring, a ring at the set
time, and no duplicate after that occurrence is served. This complements the
existing quiet-sleep, peak/decline, walking, and already-awake tests. Snooze after
the initial ring remains an explicit separate delay.

Intermediate validation rejected an older 31-test suite even after rebuilding
33 tests. Running the binary with a different filename resolved that mismatch;
the runner now uses a content-derived executable filename. The final validation
also records source/configuration/resource hashes and checks that they remain
unchanged; only the complete final series counts as evidence.

## Automated evidence

The latest three passes traced every maintained file again, first for ordinary
behavior, then for failure and boundary cases, and finally for caller/resource
consistency and verification. The lifecycle trace found that selecting Active
Alarm Mode erased a pending snooze after an interruption, including a one-time
alarm already disabled by its initial ring. Reentry now preserves pending snooze
and recent ringing; a confirmed exit explicitly cancels session state. Recovery
rejects expired ringing, future ring timestamps, and deleted alarm IDs.

Two new native regressions verify one-time snooze recovery through store reload,
the separate snooze deadline and count, stale/invalid recovery state, and explicit
session cancellation. The review also fixed sensor release outside the sampling
horizon on the exit passcode screen and stale repeat labels after Custom Days.
The unused empty application stop callback was removed. No maintained file or
declared image needed deletion.

`python3 scripts/test.py 3` compiles release and test builds for `fr265s` and
executes 35 native tests per run. The final series passed all 105 test executions
on SDK 9.2.0. Both builds completed without
compiler warnings and `git diff --check` passed. Logs are generated in
`bin/validation/tests-1.log` through `tests-3.log`.
The runner automatically checks input hashes after compilation and every run;
`bin/validation/verification.json` records those hashes and both compiled binary
hashes only after complete success. These records cover source, tests, resources,
the manifest, Jungle configuration, and runner; documentation is reviewed separately.
The suite uses synthetic sensor inputs through production ingestion methods;
it does not duplicate the algorithm in Python. Detector setup and simulated
clock helpers are excluded from release builds by the `testSupport` annotation.
The test build replaces only clock/offset reads; calendar and alarm decisions
run through the production scheduler and store.

The runner checks the complete success footer and expected test count because
the installed SDK's `monkeydo` can return exit code 1 even when every test passes.
A missing footer, test failure, timeout, or incomplete run fails validation.
The runner retries startup connection failures because macOS can return from
launching the simulator before its listener is ready. It never retries a failing test.

## Limits and device checks

No review or simulator suite can establish that software has no bugs. These
tests do not validate physical sensor accuracy, overnight battery consumption,
sound/vibration on the watch, or every UI transition.

Midnight windows and offset transitions now have dedicated tests. Calendar keys
encode local dates/times; deadlines are recalculated using the watch's current
offset. One-time records store their offset to preserve the intended local time.
An upgraded legacy one-time alarm has no original offset to recover, so its
first migration assumes the current offset; verify saved times after upgrading.

The app does not forecast offset changes or recover arbitrary manual clock
resets. Forward-jump recovery requires active evaluations no more than two
minutes apart and lasts 15 minutes. Only one alarm rings at a time; another
alarm can expire while the first is sounding. Eight completed occurrences per
alarm are retained, covering ordinary repeated-hour and adjacent-date changes,
not arbitrary travel far backward in calendar time. No future-transition GPS
lookup or extra location permission is used. See the README for user-facing policy.

On the watch, verify a short alarm while walking before its window; then verify
an alarm with no early-wake evidence reaches its deadline, snooze works, the
passcode dismisses it, and an unfinished Active Alarm exit prompt is interrupted
by a due alarm. Also interrupt the app during a short snooze and reopen Active
Alarm Mode before its deadline to verify recovery on the watch. Finally test
overnight with the usual settings and note the
heart-rate status, target/window, actual firing time, and any app interruption.
Keep a native Garmin backup alarm during that validation.
